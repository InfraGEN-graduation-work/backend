# Issue & PR Convention

## 목적과 원칙

`.github/ISSUE_TEMPLATE/`와 `.github/PULL_REQUEST_TEMPLATE.md`가 섹션 구조를 정하고, 이 문서는 섹션 안에 무엇을 쓰는지만 정한다. 템플릿 본문을 복사하지 않는다. 작성자가 사람이든 AI든 같은 규칙을 따른다.

- 템플릿의 섹션을 삭제하거나 순서를 바꾸지 않고 새 최상위 섹션을 만들지 않는다. 해당하지 않으면 "해당 없음"이라고 쓴다. 세부 구분은 `###` 소제목으로 한다.
- 확인한 사실(코드, 실행 결과)과 추정을 구분한다. 실행하지 않은 것을 통과로 쓰지 않고, 모르는 것은 "미확인"으로 쓴다.
- AI 작성 표식, 과장 표현, 비밀값(토큰, 비밀번호, 실제 `.env` 값)을 쓰지 않는다. 자동으로 붙는 요약(CodeRabbit 등)은 수정하지 않는다.

## 이슈

- 유형(Bug, Feature, Chore)에 맞는 템플릿 하나를 쓴다. 제목은 템플릿의 prefix를 따른다.
- 설명에는 현상(재현 절차, 영향 범위), 위치, 기대 동작을 쓴다. 위치는 클래스와 메서드 이름을 먼저 쓰고 줄 번호는 보조로만 쓴다. 줄 번호는 코드가 바뀌면 틀리기 때문이다.
- 문제가 여럿이면 `### 1.`, `### 2.` 소제목으로 나누고 각각 위치, 현상, 기대 동작을 쓴다.
- 예상 원인에는 코드로 확인한 것과 추정을 구분해 쓴다.
- 정책 결정이 필요한 기대 동작은 "(정책 확정 필요)"로 표시한다.
- "해야 할 일"은 체크리스트로 쓰고, 항목 하나는 검증할 수 있는 작업 하나로 한다.

## Pull Request

템플릿의 7개 섹션(설명, PR 유형, 주요 변경 사항, 테스트 결과, 관련 이슈 번호, 리뷰 시 참고사항, 체크리스트)을 모두 유지한다.

- 설명: "기존에는"(문제)과 "변경 후에는"(동작) 두 부분으로 쓴다. 커밋이 단위별로 나뉘어 있으면 그 개수를 쓴다.
- PR 유형: 실제 변경 기준으로 체크한다. 테스트, 문서, 주석 변경이 있으면 해당 항목도 체크한다.
- 주요 변경 사항: 동작 하나 단위로 `### 1.`, `### 2.` 소제목을 쓴다. 파일, 클래스, 코드는 백틱으로 쓴다. squash 머지를 쓰면 커밋 해시가 `develop` 이력에 남지 않으므로 해시를 쓰지 않는다.
- API 영향: 주요 변경 사항 안에 `### API 영향` 소제목을 둔다. 요청, 응답이 바뀌면 전후 예시와 응답 코드를 쓰고, 바뀌지 않으면 "변경 없음"으로 쓴다. 설정과 스키마 영향도 한 줄로 쓴다.
- 테스트 결과: 실행한 명령을 그대로 쓰고 통과, 실패, 미실행을 구분한다. 수정 전 실패를 확인했으면 쓴다. 실행하지 못한 검증은 이유와 함께 "미실행"으로 쓴다.
- 관련 이슈 번호: `관련 이슈: #N`으로 쓴다. 기본 브랜치가 `main`이라 `develop`으로 머지하는 PR의 `close #N`은 이슈를 닫지 않으므로(템플릿 예시의 `close`도 같다) 머지 후 직접 닫는다. `main`으로 가는 릴리스 PR은 닫을 이슈마다 `close #N`을 본문에 쓴다.
- 리뷰 시 참고사항: 동작 변경, 미검증 항목, 범위 밖으로 둔 것, 리뷰어가 볼 곳을 쓴다.
- 체크리스트: 실제로 한 것만 체크하고, 하지 못한 것은 체크하지 않고 이유를 병기한다.
