## 1. 목적

Codex가 요청 범위를 불필요하게 확대하지 않고, 검토 가능한 작은 단위로 코드를 변경하도록 한다.

이 문서는 애플리케이션 아키텍처 규칙이 아니라 개인 개발 방식과 Codex 작업 범위를 정의한다.

## 2. 기본 작업 단위

- 기본적으로 하나의 세션에서는 하나의 파일만 수정하거나 추가한다.
- 사용자가 지정한 파일이 있다면 해당 파일만 변경한다.
- 요청과 직접 관련 없는 파일은 수정하지 않는다.
- 독립적으로 분리할 수 있는 변경은 별도 세션에서 수행한다.

## 3. 여러 파일 변경의 예외

하나의 파일만 수정해서는 컴파일, 빌드 또는 테스트가 불가능한 경우 여러 파일을 변경할 수 있다.

이 경우 변경 파일들은 하나의 기능을 완성하기 위한 최소한의 응집된 변경 세트여야 한다.

허용되는 예:

- 인터페이스 변경과 해당 구현체 수정
- DTO 추가와 DTO를 직접 사용하는 Controller 수정
- Service 메서드 추가와 해당 메서드의 테스트 추가
- ErrorCode 추가와 해당 오류를 발생시키는 Service 수정
- Entity 변경과 이에 직접 영향을 받는 Converter 수정

## 4. 변경 범위 제한

여러 파일을 수정해야 하는 경우에도 다음 원칙을 지킨다.

- 빌드와 테스트에 필요한 최소 파일만 수정한다.
- 하나의 명확한 기능적 목적을 유지한다.
- 기존 코드의 무관한 부분을 함께 정리하지 않는다.
- 향후 필요할 가능성만으로 코드를 미리 추가하지 않는다.
- 요청받지 않은 패키지 이동이나 구조 변경을 하지 않는다.
- 기존 공개 API나 동작을 임의로 변경하지 않는다.

## 5. 금지 사항

다음 작업은 현재 요청과 분리한다.

- 무관한 코드 포맷 변경
- 다른 도메인의 리팩터링
- 사용하지 않는 공통화 또는 추상화
- 요청하지 않은 클래스 및 메서드 이름 변경
- 향후 사용을 예상한 선제적 구현
- 빌드나 테스트에 필요하지 않은 파일 수정

## 6. 작업 완료 보고

작업 완료 시 다음 내용을 간결하게 설명한다.

- 수정하거나 추가한 파일
- 각 파일을 변경한 이유
- 여러 파일을 변경했다면 하나의 변경 세트로 필요한 이유
- 실행한 빌드 또는 테스트
- 실행하지 못한 검증과 그 이유

## 7. 판단 기준

파일 수보다 변경 목적을 우선한다.

기본 단위는 하나의 파일이지만, 최종 작업 단위는 독립적으로 빌드하고 검증할 수 있는 가장 작은 응집된 변경 세트이다.
